# Building and packaging the sidecar

How the Runway Sidecar is built, packaged, signed and updated. For how to
*run* it, see [`sidecar.md`](sidecar.md). For the release choreography
(workflows, channels, promotion), see [`ci-cd.md`](ci-cd.md).

## Prerequisites

| Tool | Needed for | Notes |
|---|---|---|
| Python 3.12+ in the project venv | every target | `make install` |
| `pyinstaller` in the venv | every target | `pip install pyinstaller` — **not** in the project requirements |
| `codesign` | macOS targets | macOS only; ad-hoc signing (`-`) |
| `tiffutil`, `create-dmg` | `make sidecar-dmg` | macOS only; `brew install create-dmg` |
| `makensis` (NSIS) | `make sidecar-installer` | any host; the installer must be compiled **from** `dist/RunwaySidecar.exe` |

## Make targets

`make sidecar` runs the sidecar agent from source; it does not package anything.
The packaging targets are:

| Target | Host | Output |
|---|---|---|
| `make sidecar-app` | macOS only | `dist/Runway Sidecar.app`, PyInstaller bundle, ad-hoc signed and verified |
| `make sidecar-dmg` | macOS only | `dist/Runway-Sidecar-macOS-dev.dmg` (builds `sidecar-app` first) |
| `make sidecar-installer` | any | `dist/Runway-Sidecar-Windows-<version>-setup.exe`, compiled from `dist/RunwaySidecar.exe` |

`sidecar-app` exits with `sidecar-app needs macOS` elsewhere. `sidecar-installer`
exits with a message when `dist/RunwaySidecar.exe` is missing: build it on
Windows first with `pyinstaller sidecar_app/spec/windows.spec`, or copy it into
`dist/`.

## PyInstaller specs

`sidecar_app/spec/` holds four specs. They differ in target, bundle contents and
console mode.

| Spec | Target | Console | Ships |
|---|---|---|---|
| `macos.spec` | macOS `.app` | no (GUI) | tray app, `app.icns` icon, `Info.plist` with URL-scheme handler |
| `windows.spec` | Windows `.exe` | no (GUI) | tray app, `app.ico`, `win_version.py` version metadata |
| `linux.spec` | Linux tray | no (GUI) | tray app (AppIndicator / GTK) |
| `linux-cli.spec` | Linux headless CLI | yes | CLI only — no tray, no GUI toolkit |

`linux.spec` and `linux-cli.spec` are separate because the CLI must not link a
GUI toolkit: it runs on headless servers and inside slim containers.

The tray specs bundle the Python runtime, so the binaries are large; see the
update budgets below.

## Release asset naming

Names are generated by `scripts/sidecar_pkg/asset_names.py`, not written by
hand. Every release publishes:

| Platform | User-facing installer | Self-update payload |
|---|---|---|
| macOS | `Runway-Sidecar-macOS-<label>.dmg` | `Runway-Sidecar-macOS-<label>.zip` |
| Windows | `Runway-Sidecar-Windows-<label>-setup.exe` | `Runway-Sidecar-Windows-<label>.zip` |
| Linux (tray) | — | `Runway-Sidecar-Linux-<label>.tar.gz` |
| Linux (CLI) | — | `Runway-Sidecar-Linux-CLI-<label>.tar.gz` |

`<label>` is the release tag: `v3.1.0` or `v3.1.0-beta.2` for a numbered release, `edge`
for the rolling prerelease. Each asset also ships a sibling `<asset>.sha256`,
and each release ships one `SHA256SUMS.txt` covering all of them.

> The `.zip` payloads are the **self-update** artifacts — the sidecar downloads
> and swaps these in place. The `.dmg` and `-setup.exe` files are the
> user-facing installers. They are different files with different purposes.

`legacy_payload_name()` keeps a lookup for the older, `v`-stripped contract so a
hand-uploaded release in the old shape still resolves. CI never publishes that
shape.

## Signing and verification

Release signing uses **Cosign 3 modern bundles** (`.sigstore.json`,
keyless). The identity is pinned to the repository's own workflow:

```
https://github.com/s3ntin3l8/runway-ai-usage-tracker/.github/workflows/sidecar-build.yml@refs/heads/main
```

with issuer `https://token.actions.githubusercontent.com`.

Before publishing, CI verifies every portable archive with the **same Python
verifier and exact identity** the updater uses (`scripts/sidecar_pkg/signatures.py`).
Older legacy bundles fail closed — a checksum cannot substitute for a valid
signature.

Verifying a downloaded asset by hand (`cosign verify-blob` against this
identity) is documented in [`SECURITY.md`](SECURITY.md).

A read-only packaging check, without installing anything:

```bash
runway-sidecar-cli --verify-update <archive> --bundle <bundle>
```

The macOS build is **ad-hoc signed only** — not notarized, and not signed with
an Apple Developer ID. The Windows build is not code-signed with a purchased
certificate either. Each OS therefore asks once on first launch. See
[`sidecar.md`](sidecar.md#unsigned-app-warning).

## Update resource budgets

Portable update archives are limited to **256 MiB**, signature bundles to **1 MiB**,
checksum responses to **4 KiB**, and release metadata to **4 MiB**
(`scripts/sidecar_pkg/update_limits.py`).

Actual bytes are counted even if Content-Length is absent or incorrect. Overflow
is a permanent failure: the response closes, temporary bytes are removed, and the
installed copy/rollback slot remain unchanged. There is no operator override.
Local archives are rejected before hashing when oversized. Release packaging
checks the same archive/bundle budgets so legitimate packages cannot silently
outgrow the updater. Signature verification remains mandatory.

## Self-update mechanics

`--self-update` (alias `--update`) downloads, verifies and installs the latest
build, then exits. The build it replaces is kept alongside as `<name>.previous`
with its version in `<name>.previous.version`; `--rollback` swaps it back.

Self-update only works for the packaged (PyInstaller) binaries. **From-source
runs and Docker containers are notify-only** — update them with `git pull` or
by re-pulling the image.

The user-facing steps are in [`sidecar.md`](sidecar.md#updates); the update
mechanics live in `scripts/sidecar_pkg/self_update*.py`.
